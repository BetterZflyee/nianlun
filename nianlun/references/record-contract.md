# 连续记忆写入契约

宿主 AI 读原始材料，结合 `project` 返回的历史记录提炼候选。不直接复用历史助手结论作为事实。每条候选应是一个可解释的事件：哪个项目、发生了什么、什么日期、来源在哪里。与已有记录冲突时列出冲突，不覆盖。

候选 JSON 示例（合成示例，不是任何用户实际项目）：

```json
[
  {
    "op": "create_record",
    "project": "目标表内的准确项目名称",
    "title": "试点联调发现网络中断问题",
    "description": "本次试点联调发现设备间歇离线；完成情况未确认。",
    "date": "2026-10-19",
    "kind": "问题反馈",
    "status": "开放",
    "source": {
      "id": "实际会议或消息的稳定ID/事件ID",
      "name": "原始材料标题",
      "quote": "原文中支持这一事件的摘录",
      "url": "https://实际可访问的原文链接"
    },
    "site_ids": [],
    "milestone_ids": []
  }
]
```

没有 URL 时省略 `url`，不能编造。`source.id` 可以是原始文件内容哈希加事件位置；聊天事件优先原始消息 ID。项目必须精确匹配；场地/里程碑必须是真实 ID 且属于项目。`kind/status` 必须是当前表已定义的选项，不隐式创建新选项。

执行：

```sh
python3 <skill>/scripts/nianlun.py --config <配置> plan --input <候选.json> --out <计划.json>
python3 <skill>/scripts/nianlun.py --config <配置> apply --plan <计划.json> --receipt <回执.json> --yes
```

plan 只读；apply 仅在当前用户明确授权该批写入后调用。用户已直接要求“把这些记录写到这个项目”且目标清楚，不再要求一次仪式性确认。归属、状态、日期或原文不清楚时，先停下对应候选。

状态修改候选：

```json
[{"op":"update_status","role":"milestones","record_id":"真实recordId","status":"已达成"}]
```

`role` 支持 `projects/records/milestones`。生成计划时保存旧状态；执行前比较线上状态。若已改成目标值则回读后跳过；如果被改成别的状态则停止，不覆盖。

新增记录的幂等标记由来源 ID、项目 ID 和事件标题生成，连同来源信息保存到现有“详情”字段。再次执行同计划会核对并跳过相同内容；同一标记内容不同则停止。每次写入按返回 ID 回读，核对全部修改字段。

这不是云端事务或无限重试：多条写入可能前几条已成功、后续失败，回执保留已验证结果。未知结果先通过来源标记或 recordId 查询，不直接重发。不同进程同时写相同候选仍可能竞态；同一 Base 的归集任务应由现有调度串行执行。

修改候选意味着重新生成计划；不要手改计划中的 fieldId 或 cells 来扩大操作范围。脚本不接受删除、结构变更、消息发送或向他人派发待办。
