# 年轮版本管理

从产品 2.0 起，大版本用于里程碑发布，小版本用于持续改进。当前功能小版本为 **2.9**，程序与安装包使用 **2.9.2**，不命名为 3.0。

| 编号 | 使用场景 | 示例 |
| --- | --- | --- |
| 主版本 | 产品定位、数据契约或核心使用方式发生里程碑变化 | 2.x → 3.0，需要明确迁移说明 |
| 次版本 | 在现有产品上增加完整功能，兼容既有数据 | 2.0 → 2.1 |
| 修订版本 | 缺陷修复、兼容性修复、小幅文案修订 | 2.1.0 → 2.1.1 |
| 材料修订 | 同一功能版本的排版与讲稿修改 | 2.1-r1、2.1-r2 |

历史程序使用 0.5.x，历史发布材料使用 1.0 / 2.0。2.1 是统一编号的起点，不重写历史标签或把旧程序冒称为 2.0。现有 0.5.3 配置继续可读，新增来源及自动动作不会因升级被默认开启。

每次发布保留：源码提交、安装包与 SHA-256、变更记录、验收范围、使用说明、发布材料及演讲时长。旧安装包与旧材料保持原文件名和内容。2.1.1 保留为旧版修订候选，2.2.0 保留为界面回退基线；2.6.0 保留为功能小版本回退基线；2.7.0 与 2.7.1 保留为历史版本；2.8.0 为本次固定回退版本；当前 2.8.1 为报告修订候选。真实账号的新渠道采集、Windows 原生安装、不同宿主端到端验收应分别记录，不用单元测试替代。

发布前运行业务测试、安装包测试与公开文件检查。新版本安装保留配置，并备份原核心；运行中的生长任务须完成或明确恢复后再切换核心。回滚使用安装备份，保留原配置和执行回执，不能删除去重记录来“重新运行”。

本轮在 2.1 修订基础上加入项目关系可视化、批量处理和 CDBI 接入，属于功能小版本。原计划的 2.1.2 读取与交互修复随 2.2.0 一并交付，不覆盖 2.1.0 / 2.1.1 安装包。大版本保留给产品架构或核心契约的里程碑变化。

## 一天内多次改版怎么分段（2026-11-07 补）

### 问题

2026-11-07 这一天提交了 69 次，但版本号一直压在 `v2.9.2`（每次 `git tag -f`
覆盖同一个 tag）。

后果：

- **版本历史没有分段**，回退时不知道该退到哪
- tag 被反复覆盖，`v2.9.2` 一度指向了当天中午的提交，时间线错乱
- 写发布说明时无法区分「这一批修了什么」

### 规则

**按功能主题分段，不按提交数或时间硬切。** 一次完整的「问题—修复—验证」
闭环就是一个版本。参考标准：

| 特征 | 是否值得一个版本 |
|---|---|
| 引入或修好一个用户能感知的能力 | 是 |
| 修掉一类系统性缺陷（如同一逻辑在多处出错） | 是 |
| 只加测试、只改文案、只补文档 | 否，并入相邻版本 |
| 纯粹的探索性排查（未改代码） | 否，写进 docs 即可 |

### 2026-11-07 的实际分段

| 版本 | 主题 | 提交数 | 时间范围 |
|---|---|---|---|
| `v2.9.2` | 当日基线（截至 11-06） | — | — |
| `v2.9.3` | 报告与倒排底座 | 42 | 00:02–05:20 |
| `v2.9.4` | 运行时稳定性 | 10 | 05:21–07:29 |
| `v2.9.5` | 3D 星图连线 | 14 | 07:31–11:39 |
| `v2.9.6` | 交互修正与文档 | 3 | 11:41–12:02 |
| `v2.9.7` | 版本号收敛 | 1 | 18:46 |

70 次提交、5 个版本，**没有提交落在 tag 空隙外**。

### 复查清单

分段完成后跑：

```bash
# 1. 每个版本之间有多少提交
for pair in "v2.9.2 v2.9.3" "v2.9.3 v2.9.4"; do set -- $pair
  echo "$1..$2: $(git log --oneline $1..$2 | wc -l)"; done

# 2. 有没有提交没被任何 tag 覆盖
git log --oneline v2.9.7..HEAD | wc -l     # 应为 0

# 3. tag 指向的提交时间是否严格递增
for t in v2.9.2 v2.9.3 v2.9.4 v2.9.5 v2.9.6 v2.9.7; do
  echo "$t $(git log -1 --format=%ad --date=format:'%m-%d %H:%M' "$t^{commit}")"; done
```

⚠️ **`git rev-parse <tag>` 返回的是 annotated tag 对象本身的 SHA，不是提交**。
要拿提交必须用 `git rev-parse <tag>^{commit}`。我因为混用这两者，一度判断
「v2.9.3 和 v2.9.2 之间 0 次提交」，其实是查错了对象。

### 版本号本身

唯一来源是 `nianlun/scripts/version.py`。改版本只改那里，然后跑：

```bash
python3 tools/check_version_sync.py    # 有硬编码就退出码 1
```
