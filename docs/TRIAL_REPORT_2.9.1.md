# 年轮 v2.9.1 产品试用分析报告

试用时间：2026-10-26 11:04 至 11:50
试用环境：macOS，DeepSeek Harness 接入（delegated），钉钉 AI 表格四表（19 个项目、29 个里程碑、12 个场地、317 条记录）
试用方式：本机工作台、8 个 CLI 子命令、8 个本地 API 端点、15 个宿主命令中的可控部分

## 摘要

- 做了什么：核验安装状态，启动工作台，把读取、输出、写入三条链路逐项实跑，并试了宿主命令面。
- 结果：读取、输出、预演三类共 13 项通过。全量 317 条记录 6.3 秒读完，离线快照 490KB，阶段汇报产出 HTML 与 Markdown 共 62 条记录、6.1 秒，写入预演落库 0 条。
- 卡在哪：试用中发现一个数据丢失级缺陷。`bind` 命令会把配置覆盖成只剩绑定字段，静默丢掉生长、宿主、时区、DWS 路径四段配置，直接导致记忆连接显示失败、定时显示未接入、三条命令裸崩。已用试用前备份恢复，恢复后记忆连接回到正常、崩溃命令恢复可用。
- 要什么决定：`bind` 的覆盖行为是否列为 v2.9.2 首个修复项；生产表里的 test 项目是否清理；`host reports` 长时间无响应是否要单独排查。

## 二、通过的部分

### 安装与启动

运行环境自包含：uv 引导 Python 3.12，依赖装在个人目录，不污染系统环境。启动脚本先做健康探测，已有服务直接复用，不会重复起进程。工作台只绑 127.0.0.1，会话令牌放在地址井号后，不出现在服务端日志里。

### 读取链路

四个层级都能全量读出，分页完整性由 doctor 自己校验并返回 complete 字段。19 个项目里 1 个已暂停、1 个已完成、其余进行中。语义字段把等级、风险、备注、汇报链接都解析成了结构，下游不需要再猜字段名。

### 输出链路

离线快照是单文件，脱离本机服务也能双击打开，适合转发。阶段汇报同时出 HTML 与 Markdown，前者投屏转发，后者便于二次编辑。报告含 33 处溯源标记，首屏写明记录范围、读取时间与数据源，并声明"里程碑为读取时的完整计划，预期效益不代表已实现收益"，把口径风险挡在前面。

### 写入链路（只做预演）

plan 把一条候选完整翻译成目标表的单元格映射：标题、详情、项目关联、日期、类型各自落到真实字段 ID，详情里自动附加来源标题、来源标识、原文摘录与一层指纹。计划里带 binding_hash，用于防止表结构变动后误执行。全过程落库 0 条。

apply 未执行。写入契约要求明确授权，本次候选自身标注了勿执行。

### 宿主与调度

DeepSeek Harness 的接入材料完整，connection.json 把 status、pending、grow、tick 四条命令的绝对路径固化了。定时回执文件在位，负责人为 deepseek，模式为宿主托管，状态是等待核验。DSH 任务板上的每小时唤醒卡已配 cron，权限已确认，提示词里带交接协议、对账流程与铁律清单。

## 三、发现的问题

### P0 表绑定会覆盖整份配置（数据丢失级）

`bind` 在命令帮助里的自述是"只读发现并绑定现有四表，不建表"。实测它把配置文件从 10 段写成 6 段，只留格式、库标识、地址、档案、时区偏移与四表结构，丢掉了以下四段：

| 丢失段 | 内容 | 影响 |
|---|---|---|
| growth | 状态目录、记忆目录、gbrain 路径、快照输出、汇报云盘目录、生长时点 10/12/14/16/18/20、六个开关 | 自动生长与阶段汇报全部失效 |
| harness | provider deepseek、mode delegated | 宿主接入信息丢失 |
| dws_bin | DWS 可执行路径 | 后续依赖默认路径时可能找不到 dws |
| timezone | Asia/Singapore | 业务时区判断回退默认值 |

连带后果有三层：工作台的记忆连接显示为未接、定时显示为未接入、`recovery-status`、`reports`、`grow` 三条命令一律抛 `KeyError: 'growth'` 裸栈。

这不是配置本身没配好。试用前的备份显示 growth 段是完整且正确的（含六个生长时点、六个开关、云盘汇报目录）。是我执行 bind 之后配置被削掉的。已按备份恢复，恢复后 doctor 全通过、记忆连接回到已连接、recovery-status 恢复正常返回。

建议修复方向：bind 只更新 tables 一个字段，其余段落原样保留；写配置前落一份带时间戳的备份。

### P1 配置异常时报错不友好

配置缺段时，用户看到的是 Python 栈与文件行号，没有一句"配置缺少 growth 段，请重新运行接入向导"。这会把 P0 这种可修复的问题放大成"产品坏了"。

### P2 汇报任务历史命令无响应

`host reports --since 2026-10-01 --until 2026-10-31` 运行超过 3.5 分钟没有返回，也没有中间输出，已终止。进程终止后没有残留。该命令与定时唤醒里"阶段汇报"槽位共用同一条流程，若根因在前者，定时跑到汇报槽位时可能一起卡住。

### P3 宿主状态口径不一致

工作台状态报 harness 为 DeepSeek Harness（delegated），宿主状态命令报当前选中 Codex（cli 模式），配置里 harness 指向 deepseek。两者本可共存（工作流宿主与定时负责人分开），但界面没有解释这层区别，使用者无法判断此刻谁在负责。

### P4 宿主健康数据为空

`host health` 返回的 channels 与 runs 都是空结构，DeepSeek 侧没有留下通道注册或运行记录。真出问题时只能翻日志。

### P5 生产表里有测试项目

19 个项目里有一个名为 test 的项目，混在真实项目中间参与排序与统计。

### P6 已知缺陷仍在

生长写记忆页时不带 force 与 expected-revision，更新已存在的页面必然撞 revision_conflict。定时卡提示词里已写绕行方法，产品侧未修。

### 附带观察

v2.9.0 说明里提到"证据背书视觉回顾与离线图表探索"，本次 CLI 导出的报告里图表组件与内联 SVG 均为 0。图表能力挂在工作台界面的探索器上，静态导出这条路径在当前数据窗口没有产出图表。对外讲能力时需要区分"界面里有"与"导出件里有"。

## 四、设计上值得保留的部分

写入两段式，预演先出计划，执行要明确授权，中间用哈希把计划与表结构锁住。这条设计挡住了误写。

所有命令都回传 remote_mutations 计数，读操作一律为 0，让"有没有动线上数据"可以逐条核验。

本地不存业务库，四张表是唯一数据源，本机只留状态与水位线。换机器或换宿主，业务数据不用迁移。

读操作稳定在 6 秒级，317 条记录全量分页没有牺牲完整性。

## 五、试用过程的改动记录

1. 备份配置到 `/tmp/nianlun-trial/config.backup.json`，随后执行 bind，触发 P0。
2. 用备份恢复配置，表结构采用线上最新版本（含新增的"待处理"选项）。
3. 全程未执行 apply、grow、schedule-owner、shutdown，未切换定时负责人，未改动任何业务数据，各命令 remote_mutations 均为 0。
4. 生成的快照与阶段汇报留在 `/tmp/nianlun-trial/`，未上传云盘、未回填主表链接。
