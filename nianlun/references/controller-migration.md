# 合并旧听记待办任务

年轮的定时负责人只唤醒一次统一核心。听记待办提取作为其中的采集、分析与动作阶段，与项目记录、里程碑、独立记忆空间和汇报共用证据及去重回执。

## 迁移顺序

1. 盘点每个旧入口：应用计划任务、系统任务、手动命令和备份触发。保留脚本与原始日志；旧的 processed 标记不能证明待办已创建，不能整体导入成“处理成功”。
2. 页面选择来源。钉钉保持已核验的 profile；飞书需要当前电脑已安装并登录 lark-cli，勾选“我拥有的妙记”。在执行记录核验实际覆盖，不将空列表视为故障或完整会议证明。
3. 所有来源使用同一 DWS 未完成待办基线。已有旧任务或手工待办可供模型去重；相近标题会阻止自动新建并等待核验，不按标题自动完成、删除或合并。
4. 核验年轮定时负责人可用后，在旧任务所属应用停用“提取后直接写待办”的触发器。不能仅靠给 plist 文件改名来证明任务停止。年轮的锁不控制第三方脚本，两个写入器并发仍有重复风险。
5. 若保留旧采集器作来源，只让它交付证据，停止其创建待办和发送摘要的职责；不要直接把原脚本作为年轮的子命令运行。

## 可移植的外部调度提示词

> 年轮单轮生长控制器。读取用户目录下 `.local/share/nianlun/install.json`，使用其中 `python_bin` 运行 `core/scripts/host.py --config <config> tick --owner <已经核验的定时负责人>`。参数使用数组或正确引用路径，不硬编码系统 Python、macOS 日期命令或个人工号。一次触发执行一轮；业务时间、滚动补采与去重由核心决定。不要调用旧提取器，不修改绑定、扩大来源或自动批准未知动作。返回 waiting_harness 时按核心 host-contract.md 处理同一编号的分析交接并恢复原轮次；失败时报告真实原因，未知写入先对账，不盲目重跑。idle、paused 或 notify=false 时保持安静；其他结果用不超过三行报告实际动作、最多五个待办标题和需处理的缺口。以 execution 回执为准，不把 analysis 中的计划表述当成实际写入。

替换占位符时读取本安装配置与定时负责人；这段提示词不会自动取得调度所有权。Codex 原生控制器可继续沿用旧兼容路径。切换到其他宿主需先停止旧负责人，再按宿主契约接入和回读核验，不能同时注册多个负责人。

## 已实现与后续范围

已实现：滚动补采、按来源水位、缺口呈现、来源版本去重、本人待办语义去重加相近候选拦截、写后统计、可选低打扰摘要、飞书妙记可选采集、定时轮次可视化。

当前全局调度没有承诺“全部工作必在 10 分钟完成”。外部硬终止可能发生在写入中；应保留执行回执并核验，不以超时为由重跑写入。CLI 已有分步超时与互斥；后续可增加安全检查点的分批时间预算。

邮件、日历、非 @ 的项目群消息、文档变更与逐字稿按需补读可作为后续来源适配。先明确本人关系、项目范围、内容边界、分页完整性和授权，再接入统一核心；不按“可访问”推断所有内容都应持续入脑。
